Исполнитель: отдельный внутренний агент `/root/integration`. Основной эксперимент main не запускался. Допуск оставляет старую строгую ветку и научные статусы исходных reports без переприсвоения passed.

Целевой сохранённый прогон: `results/verify/readiness/finite-browser-study-v1/checks-finite-and-guards/execution.json`, stdout/stderr рядом. Exit 0, 13 tests за 6.092 секунды: семь новых проверок finite readiness и шесть существующих защит. Проверены фиксированные размеры и расписание, невозможность назвать n1 эквивалентностью, фиксированные prospective 2ms/1pp, отказы при непредусмотренном изменении runtime source, обязательный initial deep review перед cached fast path и контроль изменения свидетельств, запрет final readiness с отсутствующими gates, разграничение научного failed повторения и технического failed. Существующие проверки подтверждают отказ при подмене release commit/integrity, недопущенных direct record actions, публикации reproduction без настоящих данных и ошибочных generator наблюдениях.

Полный пробный запуск двух legacy suites ранее завершился с 28 tests, 3 failures, 3 errors и одним skip за 179.125 секунды. Этот запуск не является passed. Ошибки включали исторические synthetic fixtures с несовместимыми context/protocol, двухрежимный fixture перед действующим требованием WT-D и старую replacement recovery цепочку. Их нельзя считать успешными проверками или объяснять все одной причиной без дополнительного воспроизведения.

Отдельный read-only exact-source baseline на `8ea7ddf` сохранён в `results/verify/readiness/finite-browser-study-v1/checks-baseline-8ea7ddf`. Он воспроизвёл до finite изменений те же ошибки двухрежимного prepare fixture, admitted context в memory controller и context direct smoke/diagnostic. Четвёртый baseline сценарий остановился раньше на отсутствующем `build` каталоге изолированной копии; его результат пока не устанавливает первоначальную причину. Две другие ошибки полного legacy запуска отдельно не атрибутированы. Runtime guards ради этих fixtures не ослаблялись. Фактический startup контроллера на новой реальной ENV и допущенном AA расписании должен быть проверен отдельно перед сетью; наличие stale fixtures не подменяет такую проверку.
