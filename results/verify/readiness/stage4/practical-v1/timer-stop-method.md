## Наблюдаемое превышение

Таким образом, последний видимый отказ CPU объясняется browser, а не большим стабильным router CPU. Разница browser от 1%-границы всего .1377 процентного пункта, но по действующему правилу это реальное превышение; его нельзя округлить вниз или объявить несущественным задним числом.

Все три final-файла имеют по49 последовательных resource отсчётов. OOM deltas и throttled_usec в них равны0. Server counters: active0, warmup echoed1/received1, measurement echoed3/received3, errors0. Два netem qdisc в qdisc-after.json имеют backlog0/qlen0/drops0. Это свидетельства отсутствия видимой оставшейся нагрузки/очереди в этих snapshots, не доказательство непрерывного idle на всём интервале. Не сохранены проверки/точное время каждого stabilization attempt; из final ресурсов нельзя восстановить полный результат всех queue/freshness/deadline веток каждого attempt.

## Сопоставимость baseline и stabilization

Обнаружен структурный источник несопоставимости наблюдения. Baseline снимается после трёх секунд работы sampler, до browser launch. Stabilization сам запускает в router 11 последовательных `tc -s -j qdisc show | jq` проверок с паузами .1s, затем sleep2 и по одному `check-sample.sh fresh` в каждой роли. Эта повторяющаяся контрольная нагрузка входит в cgroup CPU, но такой же цикл не выполняется при baseline. Fresh проверяет лишь конец последнего отсчёта (`end≥now−1.5s`); он не проверяет, что начало этого CPU-интервала позже завершения нагрузочного observer. Поэтому sleep2 сам по себе не доказывает отсутствия overlap с предыдущей инспекцией.

В router-final после индекса18 заметна повторяющаяся структура: 18.832%,19.019%, затем .745%,.690%; 22.398%,15.112%, затем1.081%,1.394%; далее пики до26.546%. В отсчётах15–48 медиана5.854%, максимум26.546%,22/34 выше baseline ceil1. Это хорошо согласуется с периодическим observer work самого stabilization loop и не похоже на непрерывное остаточное насыщение. Однако raw не содержит process-level CPU accounting и timestamp каждого queue check; причинная доля tc/jq не измерена. Нельзя утверждать, что весь CPU spike доказанно вызван ими.

Browser после индекса15 имеет CPU .233–1.757%,16/34 отсчётов выше ceil1. В частности, во многих циклах примерно .3%→.8%→1.1%→1.7%→.3%. Check-sample вызывает shell/seq/tail/awk; эти команды и sampler входят в тот же cgroup. Browser launch завершён к stabilization (runner finally закрывает Chromium), но raw не содержит process snapshot, доказывающий отсутствие всех дочерних процессов. Исходные данные позволяют заключить «нет доказательства большого постоянного browser load; малая observer нагрузка и sampling phase правдоподобны», а не «истинного превышения нет».

## Корректное решение STOP и следующий шаг

STOP по текущему контракту корректен и сохраняется. Отдельный практический observed calibration gate не менял CPU stabilization и не разрешает его обходить. Нельзя использовать timer samples отдельно для green admission, увеличить ceil threshold до2/27 по этим данным, продлить wait30 до случайного прохождения либо повторять неизменённую команду.

Минимальное исправление должно прежде всего сделать проверку baseline сопоставимой с проверкой idle: одинаковая инструментальная работа и одинаковое правило выбора CPU интервалов, либо явно исключённая из обоих интервалов инспекция очередей/ресурсов. При втором варианте нужно проверять границы `sample_start=end−interval` после окончания предыдущей inspector работы, а не просто freshness конца. Важно учесть и сами check-sample команды, а не только tc/jq. Выполнение такого же контрольного цикла при baseline — допустимый кандидат, но выбор длительности/числа циклов должен следовать заранее описанному matching правилу; нельзя просто добавлять baseline секунд до появления выгодного большого максимума.

До следующего запуска требуются небольшой детерминированный regression на observer-overlap и stale interval, сохранение строгого отказа для реально повышенного idle CPU и явные per-attempt timestamp/result для baseline/idle/queue/freshness/deadline. Это проверяемое исправление измерителя, а не новый численный допуск. После исправления меняется source inventory/applicability: новый bounded timer run является проверкой исправленного измерителя, старый failed остаётся отдельным preserved результатом. Самостоятельного разрешения на main либо повтор калибровки этот review не даёт.
