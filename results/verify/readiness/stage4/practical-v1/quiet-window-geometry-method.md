# Независимая проверка геометрии quiet window

14 ноября 2026, method_review. Проверена реализация6e21bb7: stabilization_cpu.py, resources.py, sample.sh, measure.sh и tests. Новых timer данных, сетевых измерений и source edits нет.

## Заключение

Увеличение заранее фиксированного quiet window с3s до4.52s и read wait с4s до6s обосновано геометрией отбора полных интервалов. Оно не связано с наблюдёнными1.138% CPU, не повышает CPU threshold и не изменяет30s stabilization eligibility. Минимум2samples сохраняется. Это приемлемое инженерное уточнение до нового подтверждающегоtimer сбора; объявлять его гарантией получения2 строк при любых допустимых brackets нельзя.

При произвольной фазе, nominal period1.01–1.02s и3s окне первый sample, начавшийся после границы, может закончиться около2.02s, а следующий — уже после3s. Следовательно, одна выбранная строка не обязательно означает CPU нестабильность либо sampler malfunction: старое сочетание3s/min2 действительно создаёт искусственный phase-dependent отказ.

Для точечных snapshot времен с максимальным межотсчётным расстоянием H для двух полных интервалов нужна длина около3H: доH до первого допустимого начала и ещё2H на два интервала. Два10ms clock guards дают инженерную основу `3×1.5s+2×.01s=4.52s`. Новый horizon следует уже существующему max resource interval, а не последнему CPU результату. Все полные интервалы внутри него по-прежнему берутся без выбора лучших; длительность, число строк и CPU values публикуются для baseline и idle одинаково.

## Оговорка о brackets

Текущий sampler публикует `previous_before_cpu` как lower bound начала, а `current_after_cpu+10ms` как upper bound конца. Поэтому консервативный CPU bracket длиннее nominal interval на длительность предыдущего snapshot. Resources validator ограничивает nominal interval≤1.5s, но не задаёт верхнюю границу этому дополнительному времени d. Для абсолютной phase-robust гарантии в такой модели нужна как минимум `3H+2q+dmax`, а dmax текущим контрактом не задан.

Простой детерминированный пример: marker0, допустимое начало строго>10000usec, nominal snapshot after times20000/1520000/3020000/4520000usec, before=after−10000. Первая строка после границы начинается lower=10000 и исключается строгим сравнением; строка с end3020000 входит; строка с end4520000 имеет upper4530000>4520000 и исключается. Даже с H1.5s и10ms snapshot bracket остаётся одна строка. При обычном периоде1.01–1.02s4.52s имеет большой запас; пример показывает предел формулировки, а не необходимость повышать horizon до прохождения данных.

Минимальный честный вариант — принять4.52s как консервативный finite engineering horizon, явно оставить insufficient/delayed brackets причиной отказа и не писать «гарантированно минимум2 при любом interval≤1.5s». Если требуется именно математическая гарантия, прежде нужен явный допустимый dmax и новый расчёт длины из него; не следует молча подбирать dmax по будущему timer raw.

Wait6s даёт1.48s на публикацию после края4.52s и отделяет resource чтение от выбранного окна. Это запас, не гарантия: чтение/coverage/contiguous checks продолжают отбрасывать stale или задержанный sampler. Inspector команды в cgroups не должны появляться до конца quiet window. Все предыдущие исходные CPU значения и неудачные attempts сохраняются.

## Проверка до новогоtimer

Нужны deterministic phase-sweep проверки на1.01/1.02s, границы1.5s и отложенный CPU bracket; тест должен различать гарантированный ordinary-sampling случай и честный недостаточный bracket случай. Неподвижный высокий CPU внутри полного нового окна должен по-прежнему отклоняться. Все30s eligibility проверки выполняются после ожидания/чтения/сравнения: более длинное окно уменьшает число попыток, а не расширяет deadline. Пересчёт полной длительностиmain с добавленным overhead нужен до его15h admission.

Первоначальный timer STOP сохраняется. Неизменённый failed не повторяется: новый plannedtimer будет проверять исправленную геометрию и observer isolation с новым source inventory. Это заключение не является результатом нового измерения или green gate.
