# Независимая проверка observer-only плана и тихих CPU окон

14 ноября 2026, method_review. Проверка предложенного integration_audit плана, без source edits, сети или повторов. Основание — сохранённый timer STOP, timer-stop-method.md и текущие sample/check-sample/measure scripts.

## Диагностика 96 секунд

Факториал Qprobe×Rreadback, 8 фаз по12s, порядок00/10/11/01/01/11/10/00 с действиями на1s и7s каждой фазы — разумный короткий способ различить нагрузку tc/jq и чтение ресурсов от работы постоянного sampler. Оба фактора включены в каждой половине симметрично относительно времени опыта; каждый cell повторяется дважды. Это диагностическое сопоставление данного периода, не независимые научные репликации и не вероятностная оценка будущей нагрузки. Симметрия ослабляет линейный временной trend, но не произвольный drift, carryover либо фазовые эффекты.

Перед выполнением нужно зафиксировать:

- Q1 — точно текущий production цикл11 `tc|jq` с10 промежуточными sleep.1; Q0 — такая же shell/loop/sleep структура с10 такими же паузами, но без tc/jq. Если Q0 делает11sleep вместо10, это уже различие времени ожидания, которое нужно исправить или явно указать. Нельзя искусственно уравнять CPU длительности добавлением busy work: предмет проверки — реальная стоимость observer.
- R1 — точные production `check-sample fresh` команды в том же порядке ролей; R0 — отсутствие этих readbacks либо явно описанный sham. Одно не должно незаметно включать другое. Самpler, лимиты, router config и процессы сохраняются одинаковыми; Chromium и полезная сетевая нагрузка отсутствуют.
- Времена1/7s задаются относительно общего монотонного начала, записываются фактические начало/конец каждого действия и deadline miss. У длинного Q1 фактическая доза дольше Q0 — это результат, а не нарушение, пока он не пересёк следующую запланированную акцию. При пересечении не сдвигать молча последующие действия и не считать фазу валидной равной дозой.
- Сохранить все resource rows, пропуски, command stderr/exit, action times и setup/cleanup. Извлечение итогового ресурса делать после последней фазы, не добавляя скрытый Rreadback в cell00/10.
- CPU приписывать фазам по полному фактическому интервалу `[end−interval,end]`; пересекающие границу строки маркировать отдельно, не причислять целиком по end. Показывать per-cell число/длительность вошедших интервалов, все CPU значения, idle без actions и интервалы с actions. Особенно важно не усреднить короткий Q1 spike во всю12s фазу и затем объявить его отсутствующим.

Carryover boundary интервалов остаётся видимым. Один сравнительный96s опыт уже достаточен для этого узкого вопроса; подбирать фазы или повторять до красивого эффекта не нужно. Без browser load опыт не исключает residual Chromium/server работу как дополнительную причину первоначального отказа. Процессную атрибуцию всего CPU он также не доказывает, но разность определённых observer interventions существенно сильнее простой корреляции.

## Минимальный production fix: одинаковые тихие окна

Предложение отделить queue inspection от CPU оценки предпочтительнее расширения CPU допуска. Сохраняются текущие baseline ceil-percent правило,1s empty-queue check,5s pause и30s stabilization deadline. Следует одинаково выбирать **все** полные sampler интервалы внутри заранее определённого3s quiet window для baseline и каждого idle attempt; читать их после окна. Выбор последнего либо самого дешёвого интервала из него запрещён.

Необходимые границы реализации:

1. Quiet marker задаётся только после окончания всех setup/queue/readback действий во всех трёх ролях, перед общим тихим ожиданием. Если marker берётся последовательными exec в каждой роли, ранняя роль уже не имеет общего тихого старта. Нужно одно общее начало либо отдельно корректные границы для каждой роли без последующих команд в её cgroup.
2. Во время окна нет инспекций/чтений, кроме одинакового штатного sampler. Самpler — часть baseline и idle. Считывание после4s безопасно только для окон, закончившихся к marker+3s; чтение не должно расширять selectable окно до своего фактического времени. Дополнительная1s пауза нужна для публикации, но не является доказательством completeness.
3. Каждый отобранный интервал имеет finite/positive interval, последовательный sample index и удовлетворяет обеим границам. Нет row — явный недостоверный attempt, без fallback к latest/stale row или пустому max=0. Самpler delay может оставить мало строк; заранее зафиксировать minimum coverage/count и публиковать их. Даже3s при нормальном периоде чуть больше1s обычно даёт2 полных интервала, иногда меньше; требование3 было бы недостижимым по фазе.
4. Нельзя называть3s окно3s непрерывного CPU контроля: после отбора остаётся непокрытый край до первого/после последнего полного интервала. Публиковать фактический union duration и края, не заполнять их нулевым CPU. Выбор2–3 строк baseline против2–3 idle с max остаётся чувствителен к обычной вариации и допускает STOP; исправление observer mismatch не гарантирует green.
5. `/proc/uptime` имеет дискретность записи .01s, а sample.sh читает cpu.stat **до** uptime. Поэтому номинальный start==marker не доказывает исключения CPU самой команды marker. Минимум — строгая start>marker и раскрытая10ms точность; строгая причинная гарантия требует timestamp bracket CPU snapshot либо заранее фиксированного отступа после marker. Не добавлять отступ, выбранный по получившемуся CPU. Одинаковая граница в baseline/idle важнее ложной микросекундной точности.
6. Deadline30 проверяется после всех queue/wait/read операций и непосредственно перед stable publication. Если выполнение выходит за deadline, последний хороший CPU window не может сделать attempt passed. С новым ожиданием4s число возможных attempts уменьшится; это явная цена корректного наблюдения, не повод растягивать30s.

Сохранять per-attempt marker/end/read times, queue outputs+exit, исходные/выбранные CPU rows, peak baseline и idle, elapsed deadline и причины каждой ветки. Последний `role-idle.jsonl` может остаться совместимым summary, но не должен перезаписывать единственное свидетельство предыдущих отказов. Итоговый raw validator обязан проверять, что опубликованные выбранные строки действительно принадлежат source resource stream и границам окна.

Более простое исправление «поменять sleep2 на sleep4» не обеспечивает границы и снова зависит от sampler delay, поэтому недостаточно. Удаление CPU проверки для timer либо увеличение baseline максимумом текущих post-run значений меняют критерий задним числом. Вариант «сначала CPU, потом queue» оставляет загрязнение от предыдущего queue attempt; ему всё равно нужен selector полных quiet интервалов. Отдельный модуль отбора интервалов и существующий sampler без изменения численных CPU пределов — минимальная рабочая архитектура; новый фреймворк наблюдения не нужен.

Детерминированные проверки должны покрывать boundary crossing, stale/empty/duplicate samples, sample delay, исчерпанный deadline и настоящий повышенный CPU в полном quiet интервале. После source fix нужна одна новая проверка исправленного timer пути; исходный STOP и96s diagnostic остаются отдельными сохранёнными результатами. Это review плана, не допуск, не измерение и не обещание прохождения.
