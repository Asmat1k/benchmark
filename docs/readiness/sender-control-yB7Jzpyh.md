## Решение и следующее действие

Полную калибровку, A/A, monitoring, pilot/main не запускать. Пороги и исходный алгоритм не менялись. Оснований назначать увеличение Docker CPU/RAM по этим данным нет; host scheduling и паузы VM пока не исключены.

Обычный baseline-control повторять без нового измеряемого фактора не требуется. Следующий шаг — подготовить отдельный 15-секундный baseline через тот же router с синхронной трассировкой:

1. До sender дождаться первой полной записи CPU/memory/queue samplers. Сохранить TID и шкалы времени.
2. Проверить наличие доступных Linux tracepoints sched_wakeup/sched_switch и syscall enter/exit pselect6/select для sender, а также средства host scheduling. Возможности и права проверять до запуска; не подменять отсутствующий инструмент ещё одним обычным control.
3. Заранее сохранить команды и критерии. В интервалах поздних слотов сопоставить timeout, syscall return, wakeup→scheduled и host/VM scheduling. Проверить потери событий трассировки. Сохранить raw, ресурсы, pcap, permanent neighbors и исходные критерии. При отсутствии одновременной host трассы прямо ограничить выводы уровнем Linux VM.
4. Только по подтверждённой причине внести минимальное изменение и проверить коротким повтором. Принятый короткий повтор не заменяет полную калибровку и остальные условия готовности.

На данном шаге исполняемая команда нового trace-сбора ещё не подготовлена: сначала требуется read-only проверка доступности средств Linux/host. Не следует запускать calibration.sh или увеличивать ресурсы вместо этой проверки.
