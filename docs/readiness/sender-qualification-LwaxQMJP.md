## Следующий шаг

Предлагается отдельное изменение UDP sender: ограничить catch-up минимальным интервалом2.5мс между фактическими отправками. Это сохраняет абсолютный план100Гц,10000 ID и payload, но исключает более четырёх send в полуоткрытом10-мс окне. Ожидание должно продолжать принимать echo и пересчитываться после пробуждения; интервалы нельзя снова догонять после позднего wakeup. Пороги, ресурсы Docker и браузерный генератор не меняются.

Это предложение новой версии алгоритма, **в текущем разборе оно не внедрено**: первоначальное поручение о критериях оставляло такие изменения за пределами внедрения. Не требуется новый host trace для обоснования ограничения пачки; пауза ОС сама по себе остаётся и может нарушить другие границы.

Offline сценарий `new_send[i]=max(old_send[i],new_send[i−1]+2.5мс)` даёт26 late из10000,max lag45.238482мс,peak4/10мс. Это иллюстрация восстановления после уже записанных пауз, не фактический проход qualification: будущие пробуждения, обработка ответов, RTT и потери не предсказываются.

После отдельного изменения нужны короткие тесты с искусственной паузой и событиями receive, проверка всех ID/сетки/границ/RTT timestamps; затем один заранее спланированный qualification из трёх100-секундных проб. Успех всех трёх плюс целостность позволяет перейти к полной calibration. При failed/inconclusive остановиться с сохранением всех данных. Не повторять неизменённый запуск до первого успеха и не повышать cap по этому одному наблюдению.
