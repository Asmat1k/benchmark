# Согласованный дизайн калибровки этапа 2

Пользователь в этом чате отверг 40 дневных сессий, ограничил калибровку двумя часами и согласовал один полный сбор с блочным bootstrap 1/2/5 с. WT-D явно оставлен. Лимит main — 15 часов; это не лимит всей подготовки. Метод согласован до нового сбора, не выбран по прохождению исторических RTT. Исторические данные не пересчитываются.

## Величина, объём и остановка

Сохраняется разность медиан RTT сообщений профиля и каждого из двух baseline, условная по возвращённым echo. Один полный сбор: 14×10000 ID, 256 байт, 100 Гц; четыре saturation по 72 с с центральным окном 61 с. Шесть latency-подсерий, восемь отдельных directional loss-подсерий. Объём не увеличивается при широком интервале. 30–35 минут сетевого сбора; qualification примерно 5–6 минут и bandwidth трёх режимов примерно 5–10 минут выполняются отдельно пользователем. На обработку и review резервируется до 45 минут; общий план калибровки укладывается в два часа. Это оценка, не измеренный runtime новой статистики.

Коллектор до старта сети сохраняет collection-plan.json: 18 имён подсерий, отдельные forward/reverse seeds, полный статистический контракт. Порядок echo и saturation прежний. Seeds: 20261110+2i / 20261111+2i, i=0..17. Повторный запуск не является дополнительной независимой единицей. Технический отказ, несовпадение ENV/source, capture loss или нарушение ID требуют STOP и нового заранее описанного решения; автоматического повтора нет. Failed/inconclusive не разрешают добор до passed.

## Расчёт и предпосылки

Метод circular-block-medians-v1 закреплён в configs/plan.json и его схеме. В каждой latency-подсерии строится вектор из 10000 плановых слотов: фактический RTT по ID или отсутствующее значение. Reply order и исходные записи не изменяются. Циркулярный bootstrap пересэмплирует непрерывные блоки целиком вместе с индикатором выживания, длины 100/200/500 слотов. В каждом из 20000 повторений считаются медианы только вернувшихся сообщений. Seed PCG64 — первые 8 байт SHA256 строки `20261113:LABEL:BLOCK`, big endian; все seeds публикуются в результате. Исходные записи, версия кода и seeds позволяют полностью воспроизвести индексы без сохранения многогигабайтного массива.

На каждый из шести медианных интервалов выделено alpha=.04/6, двусторонний percentile interval с inverted_cdf. Берётся оболочка трёх интервалов, затем [Lprofile−Ubase,Uprofile−Lbase] для всех восьми сравнений. Каждый должен целиком лежать в target±2 мс. Оболочка исключает выбор удобной длины блока; ширина не является основанием сменить длину или объём. Отсутствие RTT в целой bootstrap-реплике делает вывод неопределённым.

На восемь ненулевых directional loss-проверок выделено alpha=.01/8: Clopper–Pearson 99.875%, с фактическими знаменателями. Нулевые профили требуют drops=0. Общая семейная ошибка не более приблизительных 5% по union bound (.04 latency + .01 loss) **только при выполнении предпосылок обоих методов**. Общая зависимость между подсериями не требует их независимого ресэмплинга для этой границы: используются одновременно покрывающие маргинальные интервалы. Конечновыборочное точное покрытие latency не заявляется.

Нужен стационарный совместный процесс RTT/выживания с короткой памятью относительно выбранных блоков, достаточно регулярной положительной плотностью около уникальной медианы и обоснованной моделью независимых Bernoulli netem drops для loss. Тренд/длительная память/изменение режима/переполнения могут нарушить условия. Константный полный ряд даёт вырожденный описательный интервал; это не свидетельство точного покрытия произвольного дискретного процесса. Теория блочного bootstrap асимптотическая: [Politis–Romano, 1994](https://doi.org/10.1080/01621459.1994.10476870), [bootstrap квантилей при слабой зависимости](https://arxiv.org/abs/1710.02537). Конкретные длины и бюджет — решение этого проекта, источники их не предписывают.

Старый lag1 и тренд публикуются без изменений. Старый IID-путь по-прежнему inconclusive при зависимости, даже с independent_units=true. Для нового зависимого метода lag1 сам по себе не означает неверности блочного интервала. Дополнительно по временному порядку проверяются RTT и индикатор выживания на лагах 500/1000/2000 слотов, граница abs(rho)>3.5/sqrt(n−lag); 20 последовательных медиан окон по 5 с, fitted drift более 2 мс или пустое окно дают inconclusive. Заполнение отсутствующих RTT медианой применяется только к диагностике, не bootstrap. Это отбраковочные эвристики, не доказательство стационарности/смешивания. Периодический ряд с сильной корреляцией через 5 с обоснованно отбраковывается.

Review требует отдельные boolean stationarity_reviewed, short_memory_reviewed, bernoulli_loss_reviewed и содержательные assumptions.stationarity/short_memory/bernoulli_loss вместе с reviewer/rationale. Нельзя выставить true по одному отсутствию флага. Необоснованная предпосылка даёт inconclusive; sender-v2 failure по-прежнему failed. Предпосылки регулярности квантиля также раскрываются в stationarity rationale. Реальный gate без версии нового метода запрещён. Все sent/reply, pcap, qdisc, contexts, sources, seeds, seal и review сохраняются; новый publication создаётся отдельно.

## Время и календарь

Три режима main при n=20/30/40/60 требуют минимум 5ч20м / 8ч / 10ч40м / 16ч соответственно (80с на run). n60 исключён бюджетом до рассмотрения overhead; выбор n20/30/40 зависит от будущего power, а 15ч также должны покрыть фактический setup и технические повторы. Если достаточная мощность достигается только при n60 или реальные затраты выходят за 15ч, STOP и новое решение пользователя, без скрытого сокращения n. A/A и monitoring остаются по 20 пар на каждое из 12 mode/profile, pilot по 5 блоков/профиль; их объёмы здесь не сокращаются. Это ещё 22ч40м обязательных окон, распределяемых по календарю.

Практический план после готовности релиза/среды: день 1 базовые gates и калибровка, дни 2–3 A/A и monitoring, день 4 pilot/power, дни 5–6 последующие разрешённые действия и main в пределах 15ч. Резерв минимум двое суток до notAfter. Этот относительный план не назначает запуск этапов 3–7. При сдвиге дат пересчитать покрытие leaf до новых допусков. Смена leaf или ENV требует новых применимых средовых gates; автоматического переноса passed нет.
