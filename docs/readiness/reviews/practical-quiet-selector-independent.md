# Независимая проверка quiet-selector

14 ноября 2026. Внутренний независимый design/code review сабагентом Codex по текущим `docker/measure.sh`, `docker/sample.sh`, `docker/check-sample.sh`, `src/analysis/resources.py`. Только чтение и этот документ; сеть, тесты и production-правки не выполнялись. Новые результаты observer-only здесь не анализируются.

## Вывод

Предложенный selector существующих rows — минимальное рабочее исправление **логической** ошибки сравнения несопоставимых интервалов: одинаково для baseline/idle выбирать полные записанные интервалы после заранее указанного quiet marker, ограничить конец фиксированными3с, прочитать после4с и сравнивать прежние max(ceil(CPU%)) по ролям. Он убирает заведомое включение setup/чтения idle, когда это видно по записанным временам. Симметричный алгоритм и прежний CPU budget сохраняют исходный смысл сравнения лучше, чем повышение допуска.

Но это **операционное приближённое окно по существующим временным меткам**, а не доказательство физически полного исключения любых observer operations. В рамках выбранной пользователем практической роли стенда такой ограниченный fix допустим при явном раскрытии этой границы и отдельной проверке конкретной причины на сохранённых/заранее заданных данных. Timestamp brackets не являются безусловным prerequisite только потому, что абсолютная гарантия недостижима. Они обязательны, если success criterion формулируется именно как доказанная полная физическая вложенность CPU-counter interval в quiet period либо новые данные обнаружат значимый snapshot skew, меняющий вывод.

## Почему10мс не ограничивают всю ошибку

`sample.sh snapshot()` сначала читает `cpu.stat`, затем memory.current, memory.events и только потом `/proc/uptime`. `/proc/uptime` в текущем представлении квантован; guard10мс учитывает его шаг, но не задаёт верхнюю границу задержки CPU-read→uptime-read. Процесс может быть вытеснен между этими чтениями. Поэтому reported start>marker+10ms ещё не означает, что соответствующий предыдущий CPU counter был прочитан после marker. Аналогично marker command может ещё завершаться после собственного чтения uptime.

Контрпример: предыдущий CPU counter снят до marker, затем sampler вытеснен; uptime для той же snapshot прочитан после marker+20ms. Следующий row получает start, проходящий selector, но его CPU delta включает часть до marker. Возможны остаточный false failure и искажение знаменателя; сохранение raw позволяет исследовать, но само по себе их не предотвращает. Условие интервал≤1.5с и freshness≤1.5с не устанавливает отдельной10мс границы snapshot skew.

Этот контрпример не требует нового maxCPU допуска. Честный вывод — ограничить смысл исправления recorded-time filtering и не объявлять всю observer contamination устранённой гарантированно. Не нужно превращать гипотетическую возможность в бесконечный новый аудит без фактического нарушения практического контроля.

## Минимальные условия реализации

- Один selector для baseline/idle; interval.start=end_usec−interval_usec строго>marker+10000µs, end_usec≤marker+3000000µs. Строгость границ закрепить тестами; не выбирать окна по CPU значениям.
- Выбор только валидных конечных interval/cpu/time и правильных role/run/sample IDs. Неполное/пустое окно не равно CPU0 и не даёт stable. По заданной фиксированной схеме должно быть достаточно полных samples; критерий минимального покрытия/числа определить заранее, а не по удачному выводу.
- Сохранять полный stream, selected IDs/rows, marker, все исключённые rows и все attempts с причинами. Сохранять очереди обеих сторон; не брать только последнюю свежую строку и не усреднять CPU вместо прежнего maxceilcomparison.
- Collect/readback выполнять после fixed4s; собственное чтение не должно попадать в окно по записанным временам. Setup baseline marker ставить после всех предусмотренных setup операций. Idle marker — после операций, загрязнение от которых предполагается исключить, одинаковым заранее фиксированным способом.
- Предел30с общий, включает очереди, ожидание, чтение и сравнение. Stable после deadline не принимается. Более длинное фиксированное ожидание нельзя тайно вынести за общий stabilization deadline.
- Monitoring-off ветка после перезапуска sampler не должна выбирать baseline или idle из пустого/перезаписанного stream; baseline сохранить отдельно. Схема selector не меняет measurement CPU guard и нормировку по cgroup limit.

## Когда brackets будут минимальным обоснованным следующим шагом

Если практическая проверка показывает остаточный отказ вследствие snapshot skew или требуется строгая вложенность, bracket самих CPU reads с обеих сторон минимально увеличивает наблюдаемость. Для вложенности предыдущий CPU-read lower bound должен быть позже допустимого начала, текущий CPU-read upper bound — не позже допустимого конца, с учётом квантования. Большие/неопределённые brackets тогда дают явное непригодное окно, не фиктивный pass. Для denominator CPU% тоже нужно раскрыть способ времени и остаточную ошибку. Просто ещё один произвольный guard вместо измерения skew проблему не решает.

На текущем теоретическом review нет основания повышать CPU thresholds, удалять failed/attempts или объявлять fix эмпирически подтверждённым. Это заключение о допустимой минимальной конструкции и её пределах; решение по фактическим данным остаётся отдельным.

## Уточнённый кандидат: консервативные timestamp brackets

После первоначального обзора предложен более строгий вариант без изменения CPU бюджета: sampler читает uptime до cpu.stat, затем сохраняет прежнее чтение uptime после CPU/memory. Для строки CPU delta записываются `cpu_window_start_lower_usec=previous_before_cpu_floor` и `cpu_window_end_upper_usec=current_after_cpu_floor+10000`. Marker читается отдельным network-none analyzer после завершения target-role inspections; quietstart=markerfloor+10000, quietend=markerfloor+3000000. Baseline/idle используют один selector, collect после4s, без fallback на прежние неограниченные rows.

**Теоретическая оценка:** эта конструкция корректно даёт консервативную вложенность CPU-counter interval в quiet window при общей монотонной VM uptime и шаге представления10ms. Нижний bracket не позже предыдущего CPU read; верхний не раньше текущего CPU read. Если весь bracket contained, сам интервал counter reads тоже contained. Дополнительное чтение до CPU не меняет разность counters; новые fields — наблюдаемость границ, не основание менять budget.

Условия корректной реализации:

- No holes проверять по исходным sample_index и непрерывности исходной последовательности/report intervals. Не требовать равенства bracket endupper следующему startlower: консервативные brackets естественно перекрываются на квантование/время snapshot.
- Missing brackets, end<start, nonfinite/negative, неправильная role/run identity, задержанные либо неполные rows дают явный непригодный interval/отказ, без молчаливого legacy fallback.
- `nonempty` — это минимум данных для вычисления max, но не доказательство покрытия всех3s. Полностью вложенные примерно1s rows сознательно оставляют края номинального окна ненаблюдёнными. Требуемое число/покрытие определить до подтверждения; публиковать selected count, duration и bracket spans. Не объявлять все3s непрерывно наблюдённым CPU idle только по одному contained row.
- Поле interval_usec и прежняя формула CPU% остаются временем прежнего after-uptime delta; brackets подтверждают вложенность, но не превращают этот знаменатель в точное время самих CPU reads. Сохранять это ограничение, не обещать отсутствие любого процента ошибки. Если skew станет значимым, сырые brackets дадут возможность его обнаружить и остановить, не подгонять CPU tolerance.
- Отдельный marker analyzer не записывает свою CPU работу в target cgroups, что решает прямое загрязнение counters marker-командой. Создание/запуск контейнера и sampler всё равно могут влиять на scheduling общей VM; это не изолированный физический стенд. Результат остаётся практическим наблюдением, а не обещанием нулевого observer effect.

При этих условиях bracket вариант предпочтительнее эвристического10ms отступа для сформулированной задачи. Новых теоретических блокеров конструкции не найдено; code/regression/empirical проверка пока не выполнялась.

## Review первой реализации bracket fix

Проверены diff `docker/sample.sh`, `docker/measure.sh`, `docs/schemas/resource.schema.json`, `src/analysis/resources.py`, новый `stabilization_cpu.py` и тесты. Без запуска тестов/сети и без изменений production.

Положительные свойства:

- Позиции shell snapshot полей после добавления before-uptime согласованы: usage2,throttled3,memory4,oom5,after6; previous_before1 переносится на следующий delta.
- Bracket поля optional в resource schema, но зависимы друг от друга; legacy rows допустимы в общем ресурсе, quiet selector требует оба поля.
- Selector использует все contained rows и прежний maxceil по каждой роли, фиксированные3s и минимум2samples, без отбора по CPU. Marker находится вне target cgroups; collect после4s. Baseline/idle используют одну функцию.
- Новый loop сохраняет уникальные queue/marker/fullstream/comparison файлы каждой попытки и проверяет общий deadline после всех шагов. Cleanup сохраняет final resource streams и sampler stderr на failed partial. Старые результаты не перезаписываются.

Замечания перед тестами:

1. **Тестовая fixture:** sample_index в `QuietCpuTests.records()` начинается1, тогда как `validate_resources` требует0. Positive tests остановятся до selector; нужно согласовать fixture и ожидаемые selected IDs.
2. **Shell errexit в функции:** вызов `quiet_cpu ... || stable=0` отключает действие `set -e` внутри всей функции в POSIX shells. Поэтому marker/read/sleep failures должны иметь явное `|| return` и нельзя рассчитывать на глобальный set-e. Последний analyzer обычно заметит пустые/частичные файлы, но это не надёжная замена проверке каждого шага.
3. **Numeric/identity validation:** `validate_resources` проверяет непрерывность/OOM/coverage/bracket inequalities, но не валидирует CPU usage numeric/nonnegative/integer и run identity. Новый quiet selector должен сам требовать соответствующий schema/identity contract перед расчётом peak; отрицательный CPU не должен превращаться в отрицательный/нулевой idle. Финальная raw schema впоследствии это откажет, однако stabilization predicate не должен публиковать false stable до неё.
4. **Диагностика ошибок selector:** при исключении `-cpu.json` не создаётся, а `-comparison.json` может остаться пустым. Полные raw attempts сохраняются, но причина доступна только в общем stderr. Желательны привязанные к attempt stderr/exit для воспроизводимой причины STOP; это требование наблюдаемости, не новый CPU budget.

Этот review не подтверждает эмпирический успех исправления. До устранения замечаний, unit/regression и одной заранее заданной применимой проверки timer/source transition к следующему сбору не заявляется.
