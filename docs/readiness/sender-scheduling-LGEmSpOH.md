# Разбор Linux-трассы UDP sender, 13 ноября 2026

**Критерий каждого 10-мс слота не выполнен: 11/1500 поздних отправок, максимум 29.820501 мс.** Новая трасса сужает причину восьми исходных пауз: основное опоздание возникает **до sched_wakeup sender**, а ожидание CPU после wakeup в Linux составляет лишь 0.015–0.430 мс. Это не объясняется длинной очередью runnable sender внутри guest; задержка таймера/обработки пробуждения Linux и остановка исполнения VM на host пока не разделены. В девятом случае обнаружена отдельная длительная работа после syscall внутри Python-обёртки диагностики.

Источник: `results/verify/diagnostic/sender-scheduling.LGEmSpOH`, запуск пользователем подготовленной команды. Shell exit0; 14:32:17–14:32:54 UTC / 17:32:17–17:32:54 МСК, включая подготовку/очистку. Для восьми исходных timeout-пауз:

Например ID181: wrapper timeout7.563374мс, wall37.306334мс, CPU0.500459мс. Сам pselect6 занимает36.865мс:36.800мс sender спит,0.036мс runnable и0.029мс числится running. Wakeup фиксируется уже на29.315694мс позже deadline. Следовательно, дополнительная очередь CPU после наблюдаемого wakeup не является основным источником этого опоздания. Причина до wakeup — позднее обслуживание таймера/пробуждения либо отсутствие исполнения guest/vCPU — без host trace не установлена. Guest trace не показывает, исполнялась ли VM на macOS в этот промежуток.

Максимальный receive wrapper wall=3.913917мс, p99=0.389584мс. У восьми timeout-корней нет receive-обработчика длительностью целого слота; это не исключает других вкладов обработки ответов в иных интервалах.

**ID953 имеет другой механизм.** Последний select ready=True: wrapper wall16.316833мс и CPU11.363875мс, но pselect6 entry→exit только4.980мс. После syscall exit до wrapper after проходит11.327644мс. На этом участке sender почти всё время числится running; receive syscall начинается позже и длится около0.005мс. Значит, нельзя считать весь select wrapper wall временем ожидания ядра. Большой участок лежит в возврате в Python и диагностических операциях вокруг него. Внутри after-usage выполняются rusage, чтение schedstat и создание объектов. GC/аллокатор/стоимость чтения — возможные причины, **конкретная функция без дополнительного профиля не установлена**. Запись process CPU подтверждает большой учитываемый CPU-вклад в этом интервале, но не даёт стек. Прежняя микропроверка ~30мкс/вызов не описывает наблюдаемый хвост около11мс после syscall. Доля, добавленная именно instrumentation, пока не установлена; постоянной поправкой это не исправляется.

У ID953 sched_waking→sched_wakeup также занимает около3.686мс, а wakeup→CPU0.044мс; даже этот случай не даёт чистого доказательства единственной причины. Длительность после syscall является отдельным существенным вкладом, который прежняя классификация «пауза select» скрывала.

## Решение

Не повторять обычный control и не повышать Docker CPU/RAM: ни quota throttling, ни memory pressure этим сбором не подтверждены. Сравнение числа поздних слотов с T6NngDpB не является оценкой улучшения или overhead: наблюдения последовательные и instrumentation различается.

Следующий причинно различающий шаг — проверить возможность привилегированной трассы scheduler macOS для потоков vCPU с явной синхронизацией host/guest и контролем потерь. Текущие ограничения доступа описаны в sender-scheduling-plan.md; неподтверждённую root-команду записи не выдаём как рабочую. До нового UDP-запуска также следует изолировать/профилировать хвост диагностической обёртки без сети; обвинять production receive или переписывать исходный алгоритм по ID953 оснований нет. Новый control без этих дополнительных измеряемых факторов не нужен. Текущая трасса обосновывает локализацию, но не разрешает полную калибровку.

При cleanup были повторные wait уже завершённых samplers (`not a child`); основной wait до остановки capture завершился успешно, полнота ресурсов отдельно проверена, поэтому эти сообщения не отменяют raw. В будущем collector исправлен: samplers ожидаются по одному с проверкой каждого результата, их PID после успешного wait очищаются. Изменение проверено `sh -n`, UDP-повтор не запускался; сохранённый collector.sh не изменён.
