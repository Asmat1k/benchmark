# Короткая диагностика UDP-отправителя, 13 ноября 2026

**Сетка 100 Гц по-прежнему не проходит приёмку.** Опоздания воспроизведены исходным алгоритмом без подробной трассировки. В трассированных пробах основная наблюдаемая задержка связана с возвратом из ожидания `select`, но единственная причина на уровне Linux/macOS/гипервизора не установлена. Подтверждённого дефекта алгоритма для исправления не найдено. Рабочие calibration_probe.py, профили, частота и acceptance не изменены.

Изучены calibration-result.md, рецензии 05-calibration.md и 06-calibration-fix.md, raw calibration.ZQRTHB2H и исправление 2cefcdb. Старый seal 141/141 проверен до и после, raw сохранён. Этот сбор **не является полной калибровкой** и не изменяет её результат «не принята». Полная calibration, A/A, monitoring, pilot и main не запускались.

## Дизайн и среда

Заранее записанный [план и критерии](../../results/verify/readiness/sender-diagnostic/plan.md): три пробы по 1500 датаграмм, 15 с отправки + до 2 с drain. После их анализа отдельно назначен baseline-control без per-call tracing. Исходный send используется через импорт с COUNT=1500; период 10000000 нс, генерация payload, select/receive, догоняющие отправки и drain сохранены. Wrapper измеряет select, receive и send через monotonic/process CPU, schedstat и rusage; добавленная стоимость и возможное смещение границ учитываются при интерпретации. t_send штатно ставится **перед** socket.send, это время вызова API, не физического выхода кадра.

Сначала сняты docker info, список контейнеров, stats, сведения macOS и 5-секундный idle Linux snapshot. VM: 2 vCPU, 4109484032 байт RAM, Linux 6.12.76-linuxkit, Docker 29.6.2/aarch64. Host: 8 CPU, 16 GiB RAM, loadavg 4.87/7.52/6.88; этот снимок не измеряет причины отдельных миллисекундных пауз. Сторонний qdrant сохранён. Образы не пересобирались, их ID и лимиты записаны в inspect.json.

Штатные compose/links.sh создают тот же маршрут browser → router → server и обратно, MTU1500/offloads проверяются setup_links. Важно: Python probes — отдельные контейнеры с **cpu.max=max**, они разделяют network namespace, но не cgroup endpoint. Лимиты browser/server нельзя приписывать отправителю. Router имеет штатный лимит 1 CPU. Запуски удерживали общий measurement lock.

## Причина и границы доказательств

В trace-пробах 52 поздних слота: у 41 непосредственно предшествует select с превышением переданного timeout более чем на 10 мс, ещё 8 — догоняющие отправки после этих пауз, 3 не объясняются этим простым правилом. Разбор всех поздних слотов сохранён в *-late-details.json. Следовательно, ожидание/возврат из select — наблюдаемое место основных пауз, а не доказанная ошибка формулы ожидания. Исходный код пересчитывает остаток до абсолютного due после каждого ответа, не добавляет новый полный период после receive.

Пример r80, ID156: запрошено 6.359 мс ожидания, измерено 38.780 мс wall, 0.543 мс CPU и 0.197 мс Linux runnable-wait. Lag=32.535 мс. Для ID1295 runnable wait достигает 17.702 мс: **планирование Linux действительно участвует в части случаев**. Однако у крупнейших пауз Linux runnable wait существенно меньше wall excess. Это совместимо с задержкой таймера/пробуждения, дескедулингом VM или host, но имеющиеся данные не разделяют эти причины. schedstat не измеряет всё время, когда VM не исполнялась на host; выборка ресурсов 1 Гц не разрешает события на 10–40 мс.

Максимальный измеренный receive wall по пробам 3.859/5.483/7.836 мс, p99≤0.726 мс. Нет свидетельства, что один обработчик ответа занимает целый слот. Несколько ответов, работа между вызовами и overhead wrapper могут вносить вклад; в трёх остаточных случаях детализации недостаточно. В частности, нельзя по этим данным объявить receive полностью непричастным. Увеличение числа опозданий при r80 по одному последовательному запуску не доказывает причинность: нет рандомизации и независимых повторов. Control подтверждает наличие проблемы без подробной трассировки, но оставляет влияние ресурсных sampler и host.

**Ресурсы Docker не изменены.** Измерения не обосновывают повышение 2→4 vCPU или RAM: нет sustained CPU saturation, quota throttling или memory pressure/OOM у probes. Изменять compose CPU endpoint тем более не исправит unrestricted cgroup sender. Гипотезу ресурсов можно проверять отдельно только с заранее заданным вмешательством и повтором; обещать исправление увеличением CPU нельзя.
