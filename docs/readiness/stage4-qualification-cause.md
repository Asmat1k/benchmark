Разбор Codex по сохранённым первичным данным; новых измерений нет. Статус failed и STOP неизменны. Исполняемые исходники, образы, ресурсы, пороги и сертификат не менялись. Все53sealed файла и134source hashes повторно проверены после offline-анализа; совпадают.

## Установленные факты

ID9150 отправлен на91501.947500мс от начала sender. Его ответ отмечен receive() на91536.352208мс (RTT34.404708мс). Следующий ID9151 по плану должен уйти на91510мс, но отметка перед send равна91567.235250мс. Между отметками отправок65.287750мс. Независимый pcap router ingress показывает65.276мс между этими ID, поэтому это реальная пауза подачи нагрузки, а не только ошибка округления/критерия.

От отметки receive ответа9150 до отметки send9151 прошло30.883042мс. К моменту receive deadline91510 и ограничение previous_send+2.5мс уже истекли. После этой отметки алгоритм больше не должен ждать таймера для9151. Следовательно, эти30.883мс относятся к исполнению receive/возврату в send loop/построению packet и задержкам выполнения процесса между этими операциями. Только по этим данным нельзя различить CPU-работу Python, GC/аллокатор, вытеснение процесса Linux и отсутствие исполнения vCPU/VM. Это локализация интервала, не доказанный стек причины.

До receive9150 также есть задержка: router browser ingress→server ingress для него0.660мс при RTT34.405мс. Остаток относится к reverse qdisc/доставке endpoint/обслуживанию receive, их отдельно измерить нельзя. Pcap не покрывает финальный reverse egress. Было бы ошибкой приписать весь RTT Python или весь sender gap ожиданию select.

Для2298 ещё одна пауза: send gap51.212мс, ingress gap51.179мс, lag42.170мс. Для7870: send gap39.753мс, ingress39.908мс, lag30.707мс. Это не единственный необычный интервал.

В секундном browser sampler интервале, охватывающем счётчики9116→9216, VM busy5.155%, probe cgroup6.241% одного ядра, VM CPU pressure delta22.199мс, throttling0/OOM0. Steal0 не доказывает непрерывное исполнение VM на macOS.

Ресурсные wall_ns сняты перед чтением /proc, а абсолютного sender start нет. Попытка точной синхронизации по OutDatagrams даёт несовместимые границы; она отвергнута и не используется в выводах. Окно эпизода выбрано по фактическим счётчикам отправок, а не по придуманному абсолютному start.

Qdrant перед запуском показывал0.12%CPU, но непрерывной статистики именно этого контейнера во время эпизода нет. Его виновность не установлена. Нет признаков quota throttling, OOM или постоянного исчерпанияCPU/RAM; увеличение ресурсов не обосновано текущими данными.

## Сопоставление с историей

Историческая Linux-трасса LGEmSpOH уже показывала два класса пауз: поздний sched_wakeup без долгого runnable wait и отдельный Python/instrumentation интервал. Эта история поддерживает необходимость разделять механизмы, но не устанавливает механизм E243q4gg: другой запуск и instrumentation. В текущем qualification запускается обычный calibration_probe.send, тяжёлых Python-обёрток usage() от старой trace-пробы нет. Убирать их здесь нечего.

## Рекомендуемый следующий шаг

Один заранее версионированный диагностический план для неизменённого рабочего sender, а не повтор qualification до passed. Цель — разделить30мс CPU-running, runnable wait и sleeping/kernel wait. Использовать Linux scheduler/syscall events, явный sender start/end mono marker, PID/TID attribution и контроль потерь trace; сохранить обычные sent/reply/pcap/resources. Избегать прежних usage()/чтений /proc вокруг каждого select. Если нужен признак GC, ограничиться минимальным start/stop callback с записью в память и явно раскрыть overhead. Даже такая диагностика не является неизменённым acceptance опытом и не засчитывается qualification.

Фиксированный объём предлагаемой диагностики: одна baseline-подсерия10000ID,256байт,100Гц, без повторов при отсутствии события. Оценка2–4минут+setup; если после подготовки нельзя обоснованно ограничить5минутами, запуск передать пользователю с caffeinate -ims и отдельными stdout/stderr/exit. Сейчас команды такого запуска нет, подготовка/измерение не выполнялись. Успех диагностики — достоверная декомпозиция наблюдённого эпизода или честный inconclusive при отсутствии события/потере trace, не timing passed. macOS trace остаётся факультативной и не становится условием допуска.

## Варианты исправления после локализации

1. Если длительный участок действительно выполняется наCPU внутри Python: заранее выделить массивы времён/ID и packet buffers, убрать лишние аллокации из критического цикла, при необходимости применить recv_into. GC отключать только после подтверждённой связи callback→пауза и проверки отсутствия циклического накопления в ограниченном окне, с восстановлением после него. Пороги/10000ID/100Гц/tag/RTT остаются прежними. Это кандидат, не доказанное исправление.
2. Если проблема в пользовательском пути отправки/ожидания и простой Python-вариант не обеспечивает временную структуру: небольшой native sender с абсолютным CLOCK_MONOTONIC расписанием, bounded catch-up2.5мс и независимой обработкой приёма. Сохранить тот же wire payload/tag,10000ID, абсолютную сетку, фактические monotonic timestamps и исходные replies. Дороже в реализации и проверке; одна замена select на clock_nanosleep не гарантирует устранения descheduling/VM pauses. Абсолютная сетка в существующем Python уже есть.
3. Если задержка от выполнения VM/guest timer: контроль согласованного фонового состава, затем при необходимости отдельно согласованная смена среды исполнения, вплоть до выделенного Linux. Остановка qdrant только с разрешения владельца; увеличение vCPU, affinity и RT priority не назначаются как доказанное средство. Это меняет средовой контракт, требует новых ENV-bound gates и календарной проверки TLS.

## Влияние на применимость

Диагностика в отдельных ignored/derived путях при неизменном production source/ENV не переписывает шесть gates этапа3, но её данные не заменяют qualification. Любое реальное исправление sender/collector внутри executable inventory создаёт новый source-bound релиз: commit/release-state, нужная сборка и пересмотр применимости каждого из шести ранних gates. Старые reports нельзя перенести подстановкой новых hashes. При изменении ресурсов/среды нужен новый фактический ENV и связанные средовые gates. После исправления нужен новый заранее записанный qualification план с тремя10000-ID пробами и STOP по первому failed/inconclusive, затем полный порядок этапа4. Исторический failed сохраняется; calibration/generator ещё not_run.

Официальные справки: [Python GC](https://docs.python.org/3.12/library/gc.html), [Linux ftrace](https://www.kernel.org/doc/html/latest/trace/ftrace.html), [clock_nanosleep](https://man7.org/linux/man-pages/man2/clock_nanosleep.2.html). Они описывают механизмы и ограничения, а не причину этого запуска.
