## Следующее действие

Обычный control повторять без нового диагностического фактора не нужно. Сначала проверить доступность Linux tracepoints sched_wakeup/sched_switch, syscall enter/exit pselect6/select и средства host scheduling, затем подготовить отдельный 15-секундный baseline с тем же алгоритмом и router. Сохранить TID sender и временные шкалы; для каждой поздней отправки сопоставить deadline, syscall entry/return, wakeup→scheduled и паузы host/VM. Проверить потери событий трассировки. Перед запуском sender синхронизировать готовность первого snapshot samplers, чтобы исключить известное неполное покрытие первых пакетов в других controls.

Команда такого нового trace-сбора пока не подготовлена: первым шагом является read-only проверка средств трассировки, а не ещё один контроль или изменение ресурсов. Оснований повышать Docker2→4 vCPU/RAM по текущим данным нет. Только после установления причины — минимальное исправление и короткий повтор с прежними критериями. Полную calibration, A/A, monitoring, pilot/main сейчас не запускать. Короткие данные не засчитываются как полная калибровка.
