# Условия перехода между сериями

Обязательны secure WS/WT-S, отрицательные TLS-пробы, закреплённые сборки/архивы, фактические ресурсы и единственный подтверждённый путь. Отдельный WT-D поддерживается при согласованном размере и точном echo. Его можно исключить до freeze с документированием причины. Включённый режим проходит соответствующие проверки.

Каждая запись checks хранит expected, actual, units, tolerance, status, reason, UTC и ссылки с SHA256. not_run означает отсутствие запуска. Итог verify — 0 только при passed всех обязательных строк, 1 при failed, 2 при неопределённости или пропущенной обязательной проверке. Обязательные условия перед пилотом проверяют в следующем порядке.

1. Один clock страницы, 100000 вызовов, монотонность, шаг и p99 overhead ≤0.1 мс. Проверить сборку рамок, целостность raw и offline-эталоны анализа.
2. До/после и по каждому профилю 10000 UDP echo по 256 байт на 100 Гц. Допуск sender v2: late≥10мс ≤1%, max lag≤50мс, ≤4 пакетов в любом окне (t−10,t]мс; все14 подсерий, без исключения tail ID. [Решение и обязательная qualification](readiness/sender-quality-v2.md). Для нового реального релиза применяются приближённые одновременные блочные интервалы по [методике этапа 2](readiness/calibration-blocks-stage2.md); исторический IID-путь сохраняется только для прежнего контракта. Разность [Lprofile−Ubase,Uprofile−Lbase] целиком внутри [2d−2,2d+2] мс. Раскрыть тренды, зависимость, survivor bias. Необоснованная стационарность/короткая память либо флаг длительной зависимости дают inconclusive; lag1 сохраняется в диагностике.
3. Для каждого egress 99.875% exact binomial CI (Bonferroni для восьми ненулевых сравнений) односторонних потерь должен включать заданную вероятность. При заданном нуле drops=0. Знаменатель reverse включает только реально поступившие туда ID. Для независимых потерь 1% в двух направлениях ожидаемая потеря UDP echo 1.99%. Saturation 60 с в направлении для loss0/lossy, 9–11 Мбит/с на заявленном tc accounting уровне. Сверить fragmentation/MTU, bytes/headers, backlog, отсутствие неожиданных overflow и <10% полосы при основной нагрузке.
4. При loss0/20 Гц miss=0, p99 lag≤5 мс, 20±0.1 Гц, CPU browser/server <70% лимита, throttling<1%, OOM=0. На 100 Гц CPU<70% и miss=0. Проверить router и очереди.
5. A/A 20 пар на каждое mode/profile, fresh процессы и разные seeds. 95% rank CI медианы ΔQ внутри ±2 мс и 95% paired bootstrap CI среднего ΔS внутри ±1 п.п. Сохранить U и разрывы. Отдельно monitoring on/off предварительно по 20 пар каждого сочетания с теми же границами и барьерами полноты. Порядок случаен, seeds одинаковы внутри on/off пары, между парами меняются. Null/широкий ДИ дают inconclusive. Наблюдать drift и ресурсы раз в секунду, 100 мс только диагностически.
6. При failed или inconclusive сохранить результаты, заранее описать исправление/новый объём/diagnostic подсерии и заново провести затронутые проверки. Запрещён добор до удобного результата. После обязательных passed официальный pilot ≥5 блоков/профиль хранится отдельно. Для n=20/30/40/60 выполнить 10000 симуляций при сдвигах 0,±5 мс, раскрыть residual resampling, неопределённость Monte Carlo, ДИ, ties/dependence/rare failures и достижимость 80% мощности.
7. Обосновать n, длительности, допуски и алгоритм A/A shift до main. Repeat tolerance по эффекту max(2 мс,p95 абсолютного A/A shift), по полноте max(1 п.п.,p95 абсолютного S shift). При изменениях версионировать методику и повторять затронутые проверки. Только затем final verify и freeze с UTC, фактическими hashes релиза/анализа/locks/configs/сертификата/расписания, чистым релизом и покрывающим серию leaf.
8. Независимо воспроизвести сборку/архив и offline результаты. При новом окружении повторить средовые gates. Запуск main требует совпадения всех версий/hashes и действительного final verify/freeze. Короткие smoke, синтетика и diagnostic хранятся отдельно. Данные пилота исключены из main.

В execution ledger поле design различает comparison (pilot/main), aa и monitoring. Для comparison modes задаёт порядок обеих обязательных сторон, при включении WT-D добавляется третья уникальная сторона. В aa/monitoring modes содержит один и тот же режим дважды. Для monitoring поле monitoring_order в том же порядке назначает on/off каждому прогону. Два сетевых seed пары on/off сохраняют в расписании и обоих manifests, в A/A стороны получают разные seeds. Baseline обозначает исходный loss0 без добавленной задержки; это значение поля profile в manifest допустимо для smoke/diagnostic/verify. Калибровочные UDP-пробы документируются отдельно в calibration evidence. Расписание пар pilot/main содержит исключительно r20p0/r20p1/r80p0/r80p1.
