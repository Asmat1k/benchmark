# Будущая экспериментальная приёмка

Эти интерфейсы реализованы в D5, но не дают разрешения на запуск в текущем поручении. Экспериментальные результаты имеют статус not_run/deferred_by_user. `make acceptance-test` проверяет алгоритмы и управление offline. Примерные успешные данные тестов существуют только во временных каталогах и не являются реальным verify/freeze.

## Выполнение и расчёты

`src/analysis/acceptance.py` реализует проверки таймера, UDP-калибровки, потерь, saturation, генератора и парной эквивалентности. Это модули обработки первичных наблюдений; получение UDP/traces/tc accounting для калибровки выполняется до их вызова в отдельном контролируемом диагностическом сборе. Модуль не выводит наблюдения из заданных netem параметров. Входные числа нельзя заменять ожидаемыми значениями. Действительные сборы и их средовая приёмка отложены.

`make calibrate ARGS='--input FILE --output REPORT --environment ENV --kind real'` рассчитывает калибровку из JSON. Аналогичные команды `timer`, `generator`, `aa`, `monitoring`, `pilot`, `power` используют тот же интерфейс. Контейнер расчёта запускается без сети и завершается до начала следующего измерения. `--kind` по умолчанию synthetic. Такой отчёт не принимается для реальной серии. Выходные файлы неизменяемы: повтор требует нового имени.

Каждый реальный вход содержит `kind: real`, `source_hashes` из `admission.sources()`, `environment` со ссылкой path/SHA256 на ENV и непустой `evidence` со ссылками на первичные файлы. ENV — фактический `context.json` стенда в формате D3: host/VM, leaf, configs, locks, images и лимиты нормализованных ролей. Перед и после каждого прогона D3 сравнивает реальный context с ENV. Для привязок файлов используется путь от корня репозитория либо абсолютный путь, который должен оставаться доступным. Примеры тестов не являются источником реальной приёмки.

Первичные проверки build/TLS/path/raw/analysis импортируются командой `experiments.py import-checks --input FILE --output REPORT --environment ENV --kind real`. Во входе указываются общие поля, `gate` и `document` по checks.schema.json. Все обязательные строки должны присутствовать в первичном документе; источник отвечает за их предметную полноту. Данные и SHA проверяются, обязательный failed даёт exit1, not_run/inconclusive — exit2. Итог verify требует все десять определённых gate; пустой перечень не проходит.

## Входные данные алгоритмов

- `timer`: поля `count=100000`, `monotonic`, `step_ms`, `p99_overhead_ms` результата страничного timerResolution. Проверяется ≤0.1 мс и монотонность.
- `calibrate`: текущий method=observed-profile-check-v1, полный контракт [здесь](readiness/practical-calibration-v1.md). echo содержит before/after и четыре профиля, sent=10000/frame_bytes=256/frequency_hz=100, полные sent/reply records и все реальные rtt_ms. observed_profile хранит все20 окон на500 плановых ID и observed envelopes; это не confidence interval. 16 egress profile/when/direction/entered_ids/dropped_ids и четыре saturation сохраняются. Loss1 .5–1.5%, loss0=0. trace_review требует явный observed_period_reviewed=true, independent_units как описательную оценку, все прежние network/integrity reviews и main_bandwidth_fraction<.1. Все14 sender-подсерий проходят late/burst/spacing и shadow proxy; missing наloss1 публикуются какunknown. Legacy circular-block-medians-v1 сохраняет прежние CI и reviews; IID доступен толькоoffline. Никакие raw/tail/missing не исключаются.
- `generator`: массив `runs`, ровно baseline20/100 Гц. Каждый содержит measurement_slots≥1200, resources_complete, router_backlog_reviewed, miss, oom, browser/server_cpu_pct_limit, browser/server_throttling_pct, lag_p99_ms и observed_hz. CPU нормируется фактическим лимитом, не одним ядром. На 20 Гц применяются lag≤5 мс, 20±.1 Гц; на обеих частотах miss0, OOM0, CPU<70%, throttling<1%.
- `aa`/`monitoring`: ссылка `schedule`, `design`, `independence_reviewed`, необязательное include_wt_d. Из полного D3 raw заново рассчитываются Q/S/U/disconnects, проверяются hashes, свежие проекты, интервалы времени и чистый релиз. Требуются ≥20 пар каждого включённого mode/profile. Monitoring вычисляет on−off, A/A side2−side1. 95% rank CI ΔQ внутри ±2 мс и paired-block bootstrap10000 CI среднего ΔS внутри ±1 п.п. Null, широкий CI или выявленная зависимость дают inconclusive; нарушение U≤1%/отсутствия disconnects — failed. Сохраняются все bootstrap indices, U, разрывы и диагностические тренды. До изменения фиксированного объёма нужна новая версия.
- `pilot`/`power`: ссылка schedule на отдельную полную официальную pilot-серию. D4 валидирует raw/ledger/audit; минимум пять полных блоков каждого профиля, null Q делает мощность недоступной. `pilot` сообщает доступные парные эффекты; содержательную проверку достаточности длительностей/очередей/редких отказов документируют в rationale. Power центрирует парные эффекты медианой профиля, пересэмплирует целые блоки, проводит ровно10000 симуляций для n20/30/40/60 и shifts0/±5, применяет full-n sign/Holm4. Отдельно моделируются ties(округление5мс), dependence(дублирование соседних units), rare failures(+100мс с p=.01). Сохраняются PCG64 state, residuals, MC99% CI, ширины/покрытие95/98.75% CI. Статус passed относится к исполнению расчёта, не доказательству80% мощности. Малый pilot и выбранные модели ограничивают вывод.

## Допуск и управление сериями

`make verify ARGS='--input REPORT_MAP --output VERIFY --environment ENV [--final]'` проверяет mapping gate→report. Недостающие gates записывает not_run/deferred_by_user с actual=null; exit0 только при обязательных passed, exit1 при failed, иначе exit2. Все evidence hashes сверяются. Научные gate вычисляются повторно из входа, поэтому ручная замена status на passed отвергается. На стадии AA достаточно build/tls/path/timer/raw/analysis/calibration/generator; monitoring требует также AA; pilot требует все десять. Final verify использует ту же методику на окончательных параметрах.

Расписание готовит `experiments.py prepare --phase aa|monitoring|pilot|main --output SERIES --environment ENV --verify VERIFY --kind real [--freeze FREEZE] [--blocks N] [--datagrams]`. Для AA/monitoring минимум20, для pilot минимум5. Расписания PCG64 случайны заранее; внутри monitoring пары одинаковы оба сетевых seeds, а между парами меняются; AA использует разные seeds сторон. Сохраняются immutable schedule-original, mutable execution schedule, ledger и admission. В main берётся расписание, связанное freeze; его series_id должен совпасть с каталогом назначения.

После будущего отдельного разрешения реальный запуск: `SERIES_TLS_DIR=/absolute/persistent/certs make experiment SERIES_DIR=results/pilot/ID ALLOW_REAL_EXPERIMENTS=yes`. Этот же интерфейс поддерживает results/verify/raw/ID для AA/monitoring и results/main/ID. На хосте нужны Make/Docker; Python/NumPy остаются в analyzer. Для каждого запуска shell получает разрешённый индекс у network-none analyzer, затем вызывает D3 measure. Общий D3 measurement lock защищает ресурсы. Выбирается первая pending сторона первого planned блока текущей queue; расписание перечитывается после каждого прогона. Уже опубликованные raw не перезаписываются. Exit3 D3 с PENDING_REPLACEMENT приводит к exit2 без дополнительного STOP; после штатной доказанной замены можно продолжить. Замены допущены только через воспроизводимые D3 audit/transaction, исходный frozen schedule не меняется. Незавершённая транзакция блокирует дальнейший трафик. Остальные сбои сохраняют STOP/evidence.

При monitoring off sampler работает до окна и после него, проверки CPU baseline/стабилизации и контекста сохраняются. Непосредственно до/после окна сравниваются cumulative memory.events; изменение останавливает серию. monitoring-window.json явно обозначает отсутствие ресурсных наблюдений окна. Не вычислять CPU окна из наблюдений до/после. Raw хранит реальные отсчёты после окна и отдельные baseline, без подстановки нулевых ресурсов. Запуски вне monitoring не могут отключать sampler.

## Freeze и main

Freeze создаётся только позже: `make freeze ARGS='--input PROPOSAL --output configs/freeze.json --kind real'`. PROPOSAL соответствует расширенной freeze.schema.json без frozen_utc, которую выставляет команда. Обязательны rationale, алгоритм AA shift, фиксированное n20/30/40/60, WT-D decision, repeat tolerances из AA p95, clean committed release, полный source_hashes, leaf_pem/series_end_utc и все12 bindings протокола/configs/анализа/locks/environment/leaf DER/schedule/final verify/pilot/power. Анализ и locks можно связать через отдельные inventory JSON с фактическими hashes; полный executable source inventory дополнительно обязателен. Финальные thresholds должны иметь preliminary=false. Leaf должен покрывать всю серию и совпадать с DER и фактически смонтированным leaf каждого прогона.

Main заново проверяет полную схему и те же существенные условия, даже если freeze создан внешним способом. Все исходники исполнения должны принадлежать чистому Git tree; пользовательский .agents/plan/ не является исходником исполнения. Изменение config/source/environment/cert/schedule/verify или synthetic evidence закрывает допуск. Реальный configs/freeze.json в D5 не создан. Релиз и архив следует независимо воспроизвести до отдельного разрешения main; D6 текущего поручения выполняет передачу разработки, экспериментальная репликация остаётся обязательным последующим этапом.

Main admission дополнительно требует `--reproduction REPORT` у prepare. Отчёт импортируется как gate=reproduction; первичный checks document должен описывать независимое воспроизведение, а `author_id` и `executor_id` должны быть непустыми и различаться. Его kind/source/environment/evidence проверяются повторно перед каждым main run. Это отдельное условие после freeze и не часть предварительного pilot verify. Имена исполнителей являются заявлением происхождения, а не механизмом криптографического удостоверения личности.

## Уточнения после независимого ревью D5

Сводки предыдущих development smoke/build не являются реальными acceptance gates. Для внешних build/TLS/path/raw/analysis/reproduction теперь обязателен предметный состав PRIMARY_IDS из collection.py. Каждый input указывает kind, gate, collection_id, environment, source_hashes, collection и evidence. Collection JSON повторяет эти пять полей идентичности и связывает payload через path/SHA256. Payload повторяет gate/collection_id и содержит первичный document/observations либо values. Для внешних gates каждая строка checks точно соответствует observation; её typed trace содержит тот же collection_id, gate, id и actual. Удаление обязательного ID, использование чужого сбора или документа другого gate закрывает допуск. Это явный контракт будущих сборщиков, а не объявление ранее полученных summaries достаточными. Экспертная оценка независимости и trace review по-прежнему документируется отдельно.

Timer payload дополнительно хранит100001 clock_samples_ms; count, step, monotonic и p99 заново выводятся из этих отсчётов. Calibration latency probe содержит sent_records[{id,t_plan_ms,t_send_ms}], reply_records[{id,rtt_ms}], а rtt_ms точно соответствует возвращённым ID. Прямые/обратные loss counts относятся к отдельным полным probe подсериям: одинаковый collection_id в паре egress, probe на forward,10000 исходящих ID, обратный вход равен forward survivors, reply IDs равны reverse survivors. Отдельный latency collection и loss collection не смешиваются; полнота проверяется для каждого. Номинальная100Hz grid проверяется по каждому исходящему слоту; UDP отправки оцениваются по `udp_sender` v2: late≥10мс ≤1%, max lag≤50мс, ≤4 пакетов в любом полуоткрытом окне10мс. Прежний every-slot сохраняется описательно; ограничения одинаковы для всех14 подсерий. Generator хранит slots, resource_samples/resource_window; frequency grid, miss, lag, CPU относительно cpu_limit, throttling и OOM пересчитываются по этим рядам. Численная полнота/неотрицательность обязательны;100Hz label не может описывать20Hz сетку. Браузерный generator gate сохранён; UDP v2 к нему не применяется. Обоснование, конечные условия и оставшаяся qualification: [sender-quality-v2](readiness/sender-quality-v2.md).

Host-команды запускают docker/release-state.sh: git archive HEAD поступает в короткий analyzer без сети, который сохраняет commit и SHA256 содержимого committed tree в build/release-state.json. Git внутри analyzer не требуется. release() сверяет фактический executable source inventory с этим снимком; изменённый/новый/удалённый исходник закрывает допуск. Снимок создаётся один раз перед initial/restart controller. Controller передаёт принятый admission.release_commit в ready; непосредственно перед compose up host сравнивает текущий HEAD с этим SHA и проверяет чистоту тех же исходных путей через docker/check-release.sh. Смена даже docs-only commit останавливает запуск до сети. Повтор архива или научных расчётов перед каждым прогоном не выполняется. Generated results и пользовательский .agents/plan не определяют dirty; D3 фиксирует dirty только по путям исполнения. Прямому Python API release() нужен заранее созданный host snapshot. Snapshot — состояние текущего host checkout, его нельзя переносить между релизами без повторного создания.

A/A и monitoring случайны только внутри каждой из четырёх последовательных сессий. Режимы и профили сбалансированы внутри сессии. Исполнение сверяет current.runs полностью с выводом block_runs, ledger с metadata, queue с исходным порядком и доказанными deterministic replacement insertions. Пустая queue при planned ledger или отсутствующем raw не означает complete. results/main и results/pilot нельзя использовать для smoke/verify обхода admission.

Расчёт официального отчёта требует предварительный admission, полную исходную принятую schedule, совпадающие context/source/release и точную folder/run attribution. Используется тот же полный raw/audit validator, что у D4, с явно заданным дизайном. В метрики и evidence попадают действующие complete attempts; quarantined attempts проверяются целиком в audit. SYNTHETIC.json закрывает реальный допуск. Изолированные offline fixtures могут явно использовать kind=synthetic, synthetic verify и admission только вне рабочего results; такой путь не допускается real executor и real freeze. Для теста JSON roundtrip AA/monitoring допускается отдельный synthetic pairs input; реальные отчёты всегда читают полные raw.

Freeze требует точные report.gate=pilot/power и один и тот же исходный pilot schedule для обоих. Покрытие режимов проверяется в AA/monitoring до pilot, затем в pilot/power до main. Analysis inventory имеет вид files={path:SHA256} и точно покрывает src/analysis; locks inventory точно покрывает установленный перечень файлов зависимостей, включая OS manifest. Посторонний файл с корректным SHA не является inventory.

Минимальный certificate horizon составляет80с на каждый оставшийся обязательный прогон; это нижняя граница warmup/measurement/drain/pause, а не оценка startup overhead. При выпуске freeze учитывается весь schedule, при продолжении — фактически оставшиеся active runs с учётом замен. Заявленный series_end_utc и leaf должны покрывать эту границу; окончательный план обязан дополнительно предусмотреть фактический overhead, установленный будущим пилотом.

Для действительного verify также явно задают `--kind real`; значение по умолчанию synthetic предназначено для offline примеров. `collection.schema.json` и `primary-payload.schema.json` формально проверяют оболочку сбора и предметный payload. Импортируемые строки представляют named boolean predicates: expected=true, actual=true/false и согласованный passed/failed. Непроверенная или не выполненная predicate должна иметь соответствующий inconclusive/not_run, а не фиктивное true. Связанный typed trace хранит actual и идентификаторы конкретного сбора; исходные команды/логи и экспертное обоснование сохраняются в evidence будущего сборщика.

## Полная приёмка и допуск отдельного прогона

Публикация отчёта и полный verify пересчитывают научный результат по первичным данным. Отчёт дополнительно фиксирует integrity: SHA256 всех транзитивно связанных файлов и точный состав деревьев входных серий, включая raw/audit/context/admission и underlying primary collections. Derived исключён из immutable входов. Выходной отчёт размещают вне входного дерева либо в derived. После изменения первичных данных требуется новая приёмка, а не обновление одного report SHA.

Per-run admit, record.prepare и context проверяют эту замкнутую целостность, schemas, source/release/environment и guards без повторного разбора слотов, bootstrap и power по всей предыстории. Самостоятельное завершение next/execute сохраняет полный контроль завершённой серии; при публикации completed_series выполняет эту полную проверку ровно один раз. Ранний опубликованный член пары до next обязан иметь совпадающую identity, полный перечень raw, корректные SHA и completion1200. Quarantined попытка требует настоящую замену и transaction/proof. Правомерные API failures генератора дают failed; невозможное соответствие send_state/t_send или непокрытое ресурсами окно — отказ входных инвариантов.

Leaf проверяется раздельно: notBefore≤текущее UTC, а notAfter и series_end покрывают оставшиеся обязательные окна. Offline тест задаёт фиксированные часы, поэтому срок архивного fixture-сертификата не меняет вердикт тестов.

## Доверенный управляющий процесс (R11a)

Файл integrity сам по себе не даёт быстрого допуска. `make experiment` держит один analyzer controller по stdin/stdout с FIFO на хосте, без сети и без Docker socket. До ответа ready и до запуска измерительных сервисов controller выполняет полный admission; для main сюда входят verify, предоставленный извне freeze, pilot/power и reproduction. После остановки или возобновления сеанса проверка выполняется заново.

Только этот процесс хранит в памяти результат глубокой проверки: canonical graph фактических первичных ссылок, проверенные gate fingerprints и anchor admission. Перечень зависимостей выводится из typed primary материалов, а не заимствуется из вложенного integrity. Header kind/gate/source/ENV и содержимое канонических зависимостей продолжают проверяться. Исключённая из предъявленного receipt primary-запись либо изменение underlying observation закрывают fast path. Память не восстанавливается из файла, флага окружения или самого предъявленного отчёта.

Host `docker/experiment.sh` передаёт prepare/context/complete тому же controller через унаследованный поток; D3 measurement lock использует отдельный дескриптор. Прямые next/record.prepare для экспериментальной серии без этого контекста отказывают. CLI prepare выполняет полную первоначальную проверку, но не выдаёт долговечного полномочия будущему процессу. Для обычных D3 smoke/diagnostic интерфейсы сохранены. Новый `make controller-test` проверяет настоящий CLI-контрпример, initial/restart, shell FIFO и отсутствие повторных scientific вызовов при RPC. Полная публикация и явный полный verify по-прежнему пересчитывают научные результаты.

При initial real admission поле release_commit дополнительно сверяется с release() до выдачи ready. Поэтому SHA в ready уже связан с проверенным release-state, а не просто прочитан из предъявленного admission.

### Независимый сетевой повтор перед main

Для `import-checks` с gate=reproduction проверяющий передаёт ссылки path/SHA256 `freeze`, `reference_schedule` и `repeat_schedule`. Эталон — завершённый официальный pilot, на который указывает pilot report конкретного freeze. После freeze отдельный исполнитель заранее готовит новый pilot того же фиксированного объёма с новым series_id, теми же профилями и решением WT-D. В новом окружении его admission требует актуальных gates именно этого окружения. Все повторные raw остаются в отдельном pilot-каталоге. Поле environment у reproduction идентифицирует проверяемый freeze, а admission повтора фиксирует фактическую среду повторных измерений.

Проверка пересчитывает D4 из двух полных raw, сравнивает по каждому профилю сдвиг медианы парных разностей Q и сдвиг среднего парных разностей S по включительным границам repeat_effect_ms и repeat_fullness_pp из freeze. Неопределимый Q или выход за допуск дают inconclusive, нарушение полноты даёт failed. Независимый исполнитель оценивает интервалы, практические решения и дрейф отдельной обязательной строкой interval-decision-drift-review. Результат сохраняет исходные интервалы, решения, наклон и lag1 обеих серий. Штатный import и глубокая проверка выполняют полный пересчёт, а контроллер между прогонами использует проверенную целостность. Изменение freeze требует нового reproduction.

Freeze ссылается на неизменяемую копию первоначального main-плана вне рабочего schedule.json. Например, сохраните исходник как configs/frozen-schedules/ID.json. Его series_id определяет имя будущего каталога. При доказанной замене обновляется только отдельное рабочее расписание серии. Prepare проверяет весь admission во временном каталоге перед публикацией. В существующем main-каталоге с тем же стартовым расписанием admission публикуется последним. Повтор после прерывания между ledger и admission проверяет точное совпадение начального ledger.
