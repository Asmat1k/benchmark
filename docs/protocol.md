# Протокол обмена

Машинный контракт версии 1 хранится в [configs/contracts/protocol.json](../configs/contracts/protocol.json). Параметры нагрузки, пороги и сетевые профили — в [configs/](../configs). Текущие правила сбора определены [exploratory-browser-study-v2](../configs/policies/exploratory.json); прежние строгие правила не являются описанием этого режима.

Chromium подключается к `https://bench.test:8443`. Go-сервер обслуживает WebSocket по TCP HTTP/1.1 `/ws` и WebTransport по UDP HTTP/3 `/wt`. Используется TLS 1.3; браузер доверяет CA, WebTransport проверяет SHA-256 DER сертификата. Компрессия WS и переподключение в ходе измерения не используются.

Перед измерением клиент передаёт ASCII `READY`, сервер возвращает `ACK` по выбранному каналу. WS переносит один бинарный кадр сообщением, WT-S — последовательность кадров в одном двунаправленном потоке, WT-D — один кадр датаграммой. Для WT-D требуется maxDatagramSize≥256. Сервер возвращает кадр побайтно.

Рамка содержит 256 байт; многобайтовые поля big-endian:

| Байты | Поле |
|---|---|
| 0–3 | magic `0x42575431` |
| 4 | версия 1 |
| 5 | фаза: 0 — прогрев, 1 — измерение |
| 6–7 | нули |
| 8–15 | nonce, uint64 |
| 16–23 | sequence, uint64 |
| 24–255 | байт на смещении i: `(sequence+i) mod 256` |

ID состоит из nonce, phase и sequence; нумерация начинается с нуля в каждой фазе. В JSON uint64 сохраняются десятичными строками. Первый правильный ответ определяет RTT; повреждения, неизвестные ID, дубликаты, ошибки записи и разрывы сохраняются событиями.

Сетка — 50 мс, 200 прогревочных и 1200 измерительных слотов. Дедлайн 100 мс и горизонт 5000 мс отсчитываются от планового времени слота, границы включительны. Пропущенные слоты не догоняются. Приложение ограничивает локальную очередь 1 МиБ.

Каждый запуск создаёт свежие сервер, Chromium, соединение и netem. Поток идёт через две внутренние подсети и router, без опубликованных портов и обходного пути. Профили добавляют по 10/40 мс и 0/1% потерь на направление, ограничивают скорость 10 Мбит/с; MTU 1500. Маршруты, настройки и seeds читаются до и после измерения.

Хеши, схемы, ID, часы, TLS, полнота логов и ресурсов проверяются перед признанием raw валидным. В текущем режиме конечные очереди и CPU recovery — наблюдения; отдельный отказ сохраняется и после очистки допускает следующее назначение. Это не отменяет проверок целостности и не превращает неизвестные данные в измеренную потерю.
