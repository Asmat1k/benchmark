# Предварительный анализ версии 1

Основные сравнения — WS и WT-S внутри каждого из четырёх профилей. WT-D описывается отдельно. Предварительно 20 блоков на профиль и 4 сессии с пятью такими блоками в каждой. PCG64/SeedSequence с master 20261108 заранее определяет порядок блоков и режимов, раздельные ветви для серий, расписания, потерь вперёд/назад, bootstrap и power. Прогоны последовательны. Пары связываются по series/session/profile/block/attempt. Seed не удостоверяет независимость.

Для каждого блока D = Q_WT-S − Q_WS, θ оценивает медиану D. Двусторонняя H0 требует одновременно P(D>0)≤1/2 и P(D<0)≤1/2. При полном n, включая связи, N+ и N− — числа строго положительных и отрицательных D. Для B~Bin(n, .5) p=min(1, 2 min(P(B≥N+),P(B≥N−))). Holm4 сортирует четыре p, умножает по порядку на 4,3,2,1, берёт накопленный максимум и ограничивает 1, восстанавливает исходный порядок. Отклонение при p_adj<.05. Любой null Q в основной паре оставляет профиль unavailable, в Holm4 вносится placeholder 1. Такой результат не интерпретируют как проверенную H0.

Для каждой медианы показать 95% и 98.75% интервал. При α берут максимальное k с 2P(B≤k−1)≤α. Интервал [D_(k),D_(n−k+1)] с D_(0)=−∞, D_(n+1)=+∞. Для n=20 ранги [6,15]/[5,16], при n=5 95% интервал бесконечен. Оценка φ — среднее парных S_WT-S−S_WS в п.п. Для каждого профиля 10000 раз выбрать с возвращением n целых блоков, сохраняя обе стороны пары. Из средних разностей взять linear percentile .00625/.99375. Сохранить seed и indices. Для WT-D показать описательные 95% ДИ среднего S и медианы прогонных Q, явно указать null. Вырожденный bootstrap крайних долей не исключает редких отказов.

По одновременному ДИ θ верхняя граница <−5 мс поддерживает WT-S, нижняя >5 мс поддерживает WS. Интервал внутри [−5,+5] поддерживает практически малую разницу, прочие пересечения дают неопределённость. Для полезного выигрыша каждый основной прогон должен иметь U≤1%, без разрывов обоих режимов. Для WT-S нужна нижняя граница ДИ φ≥−1 п.п., для WS верхняя≤+1. Статистический, практический вывод, полнота и валидность отражаются отдельно по профилям.

Эталоны sign для 20 нулей, 10 единиц+10 нулей, 10 отрицательных+10 положительных дают p=1. Для 20 единиц p=2/2²⁰, для [1..5] p=.0625. Holm для [.01,.04,.03,.002] даёт [.03,.06,.06,.008]. Константа ΔS=−.5 даёт обе границы −.5. До расчётов проверяют checksums, схемы, completion, ledger, парность и счётчики. При повторе counts, ID, ранги, решения и знаки бесконечностей совпадают точно, конечные числа с абсолютным допуском 1e−10, bootstrap по сохранённым indices.

## Реализация D4

`make analyze SERIES=path/to/series` из корня проекта запускает закреплённый analyzer без сети после измерений. Нужен образ `wswt-bench-analyzer:dev` из `make build` либо принятого архива. Та же команда работает с абсолютным путём. Общая measurement-блокировка исключает одновременную работу с измерителем. Поддержан comparison design; A/A и monitoring имеют отдельные будущие потребители D5.

Сначала проверяются schedule/ledger, уникальность attempts/runs, полные стороны WS/WT-S, отсутствие незавершённых попыток/STOP/pending replacement, однородность режимов и версий. Имя каждого каталога обязано совпадать с manifest.run_id и всеми полями назначенного run. Для каждого выбранного raw обязательно вызывается `validate_raw` D3: checksums, schemas, completion, события/слоты/ресурсы, counters, config/context, leaf, network и seeds. Дополнительно отвергаются нечисловые бесконечности raw. Подписанные снимки расписания должны содержать тот же полный исходный состав; последующие изменения допускают только сохранение исходных заданий и добавление замен в конец. Удаление всего блока или профиля не считается полной серией, даже если верхние schedule/ledger согласованно сокращены. Фиксированное эмпирическое n не подставляется.

Исключённый технический блок должен иметь воспроизводимое доказательство в audit и единственную замену целого блока; исходы SUT не исключаются. Проверяются все каталоги, перечисленные transaction.moves, их ID/режимы, снимки расписания и целостность остальных сторон, а replacement связывается с текущим ledger. Если другая сторона не была собрана до остановки, её отсутствие допустимо только вне списка moves. Любое нарушение останавливает расчёт. Старый derived остаётся до успешного нового расчёта, поэтому после неуспешного запуска его нельзя принимать за новый результат. Comparison CLI отвергает smoke независимо от профиля и числа блоков; короткие smoke не получают статистических выводов. Полная явно синтетическая diagnostic comparison остаётся допустимым входом для разработки.

Если источник доказанной замены имеет hash-дефект, его собственный исключённый schedule не обязан семантически соответствовать утверждённому плану: повреждённые bytes сохраняются и обязаны точно совпадать с proof.files, а D3 detect повторно воспроизводит тот же hash-дефект. Идентичность источника по имени/manifest/назначенному run проверяется всегда. Независимый audit/schedule.json, transaction, все остальные архивированные стороны и каждый действующий raw сохраняют строгую проверку состава и расписания. Подмена источника или evidence после proof и усечение действующего плана не допускаются.

Выход в `SERIES/derived/`: `runs.csv`, `pairs.csv`, `profiles.csv`, `descriptive.csv`, `audit.csv`, `analysis.json`, `bootstrap-<profile>.npz`, `figures/` и `SHA256SUMS`. В JSON отсутствие Q — null с reason, бесконечность — строка `+inf`/`-inf` по контракту D0; JSON NaN/Infinity запрещены. В CSV отсутствие — `NA`, бесконечные числовые границы — `inf`/`-inf`. В CSV IDs и seed сохраняются как десятичный текст; при чтении pandas нужно явно задавать строковый dtype для ID/nonce/seeds. Единицы зафиксированы в именах колонок и `analysis.json`: ms, percent, percentage_points. CPU диагностика в runs выражена относительно одного ядра, throttled_usec — суммарное время; это не средовой gate. Queue максимум вычисляется только по наблюдённым значениям; при одних scheduler_miss очередь не наблюдалась, максимум null/NA и queue_observations=0. Все пропуски сохраняются в знаменателях. audit.csv всегда имеет одинаковые именованные колонки, включая пустую таблицу без замен.

run_order задаёт фактическую последовательность по manifest.started_utc с проверкой started<ended и отсутствия перекрытия прогонов. UTC служит только аудиту порядка, RTT по-прежнему вычисляется по performance.now браузера. Неоднозначные или перекрывающиеся интервалы приводят к отказу, а массив schedule.runs не подменяет хронологию. started_utc/ended_utc сохранены в runs и plotting CSV. Синтетический generator задаёт различимые последовательные UTC внутри срока template leaf.

`analysis.json` содержит полное n и null, ties/sign/Holm4, ранги/номинальное покрытие 95/98.75% CI, mean ΔS и его 98.75% CI, описательные 95% WT-D CI, отдельные решения/барьеры, пороги и ограничения. Отсутствующий профиль сохраняется как unavailable с p=1 в семье из четырёх. `useful_gain` требует одновременно значимости, практического интервала, полноты каждого прогона и допуска ΔS. `validity_gate=passed` означает проверку raw, а не экспериментальную готовность. Ни одна метрика не переводит отложенные экспериментальные gates в passed.

Bootstrap использует отдельную ветвь 6 `schedule.seeds`, PCG64/SeedSequence master20261108, series/series_id и индекс профиля 0..3. Каждый NPZ содержит int64 `indices` формы (10000,n), индексирующие `provenance.bootstrap[profile].blocks` в порядке pairs.csv; пары и WT-D используют те же индексы. В provenance сохранены SHA файла и state_before, schedule/ledger/context/raw hashes, hashes анализа/requirements и версии библиотек. Для точного повторения загрузите `np.load(path)['indices']` и передайте их в `inference.bootstrap`. Генератор восстанавливается присваиванием `rng.bit_generator.state = state_before` перед `rng.integers(0,n,size=(10000,n))`.

Фигуры Q/S/U, порядок/сессии, условная ECDF, парные эффекты и WT-D экспортируются в PNG300dpi/SVG/PDF. Каждая точка распределений — прогон; ECDF описывает только завершённые сообщения и показывает n завершённых/запланированных. Интервалы заранее рассчитаны, автоматический bootstrap Seaborn не используется. Бесконечные интервалы подписаны текстом без конечной подстановки; null показаны счётчиком NA. Рядом находятся исходные plotting CSV, plot-spec/rcParams, font SHA и размеры. SVG/PDF metadata дат отключена. Исходные synthetic evidence не перезаписываются обычным analyze.

## Синтетическое воспроизведение

`make analysis-test` выполняет reference, exact enumeration, integrity, audit/replacement, normal CLI и offline replay тесты внутри закреплённого analyzer без сети. CI запускает те же тесты и D0 schema fixtures; network smoke в CI записан not_run без объявления экспериментальной приёмки.

Для проверки штатного Make entrypoint создайте новый каталог (команда не перезаписывает существующий):

```sh
docker run --rm --network none -e PYTHONDONTWRITEBYTECODE=1 -v "$PWD:/bench" -w /bench wswt-bench-analyzer:dev python src/analysis/synthetic.py build/d4-reproduction --blocks 2
make analyze SERIES=build/d4-reproduction
```

Generator не создаёт трафик. Он копирует публичные метаданные принятого D3 smoke.OWQv8a3D как явно обозначенный synthetic template и создаёт все 200 warmup +1200 measurement слотов каждого режима. Серия diagnostic, 2 блока/профиль, WS/WT-S/WT-D: всего24 прогона,28800 measurement слотов. RTT WS=20/40/60/80 мс по профилям, WT-S на10 мс меньше с6 потерями каждого прогона, WT-D на5 мс больше WS. Во всех парах ΔS=−.5 п.п.; U_WT-S=.5%, Q основной эффект−10 мс, но n2 даёт бесконечные rank CI и неопределённый практический вывод. Эти числа проверяют программу и не являются данными опыта. Маркер `SYNTHETIC.json`, provenance и отчёт явно сохраняют происхождение. Принятые historical raw не изменяются.
